Overview

What PayFlow Lab is

A learning-grade payment aggregator: merchants integrate against one standardized API, and PayFlow routes each payment to one of nine payment service providers (PSPs), handling the messy reality of real payments — async webhooks, retries, failover, stuck payments, and reconciliation.

Every payment is simulated (no real money), which is exactly what makes it useful: you can generate thousands of transactions, deliberately break a provider, and practise diagnosing incidents the way a Payment Integration Specialist does on the job.

routing

Capability-aware

Each PSP supports specific currencies & methods; routing picks eligible providers by weighted or performance strategy.

async

Real webhooks

Outcomes arrive later via signed webhooks — sometimes late, duplicated, or never.

resilience

Retry & failover

Technical failures fail over to the next provider; timeouts verify before retrying to avoid double charges.

finance

Reconciliation

Compares our ledger against the PSP ledger and flags mismatches, missing records, and duplicates.

ops

Fault injection

Break a provider on demand or run a blind incident drill, then diagnose it from the dashboard.

observability

Transaction log

Every state change is a searchable event — filter by type, provider, reference, and time window.

Getting started

Run it & make your first payment

PayFlow Lab is deployed and live. The same server hosts the API, the operations dashboard, and the merchant store.

Cold start

On the free hosting tier the service sleeps after ~15 minutes idle. The first request then takes ~30–60s to wake it. Open /health first, then use the app.

Fill it with data

  1. Dashboard button — Overview tab → Start simulation (e.g. 300 payments at 150/sec).
  2. Merchant store — open /merchant, tap Pay now; the payment runs the full pipeline and appears on the Transactions tab.
Free-tier tip

On the free instance (1 CPU), keep simulations modest (say 50–150) so webhook delivery keeps up. Very large bursts can leave payments sitting in pending until the backlog drains.

Run locally

# needs Docker (for Postgres) + Node 22

npm run migrate
npm run web:install && npm run web:build
npm run dev                   # http://localhost:3000

Guide

The merchant store

A demo storefront at /merchant that behaves like a real merchant integration: it holds no data of its own and simply calls the aggregator's API. Pick an amount, currency, and method, tap Pay now, and it polls for the outcome — which then shows up on the dashboard.

Why does it keep choosing one provider?

Routing is weighted-random across all eligible providers for that currency + method. Over a handful of purchases it can look skewed — especially mobile-money / bank-transfer combos where only two providers qualify. Run a simulation or ~10 card+ZAR purchases and you'll see the spread.

Guide

Core concepts

Payment lifecycle

created → processing → pending → success | declined | failed
                                   success → refunded

Amounts are stored in minor units (cents/kobo) as integers — 49900 means 499.00.

Routing

  • rules — deterministic priority by base weight.
  • weighted — distribute across eligible providers by weight (default).
  • performance — prefer providers with a healthy recent success rate.

Idempotency

Send an Idempotency-Key header on POST /payments. A repeat with the same key returns the original payment; the same key with a different body is a 409.

Webhooks & retries

Most payments return pending immediately; the terminal outcome arrives later via a signed, deduplicated webhook. Technical failures fail over to the next provider; on a timeout, PayFlow verifies before retrying so a charge that went through is never repeated.

Reconciliation

The PSP keeps its own ground-truth ledger. Reconciliation compares it against ours and reports STATUS_MISMATCH, AMOUNT_MISMATCH, MISSING_AT_PSP, MISSING_IN_AGGREGATOR, and DUPLICATE.

Faults & incident drills

Inject faults (expired credentials, timeouts, killed webhooks, degraded approval). An incident drill applies a hidden fault to a random provider; you diagnose it, then resolve to reveal the root cause.

Reference

API overview & auth

REST over JSON. All amounts are integers in minor units. Base URL:

https://payflow-lab.onrender.com/api/v1

Error envelope:

{ "error": { "code": "VALIDATION_ERROR", "message": "..." } }

Authentication

Merchant and read endpoints are open. Admin endpoints are protected only when the server has an ADMIN_API_KEY set — then they require x-admin-key: <your key>. Endpoints below are tagged admin where the key applies.

Troubleshooting

Using the app

Dashboard / merchant store is empty no data

No traffic yet. Overview → Start simulation, or pay on /merchant.

Dashboard buttons do nothing / 401 UNAUTHORIZED

Admin actions are gated by ADMIN_API_KEY, which the browser doesn't send. Remove that env var, or call the API with the x-admin-key header.

Every payment picks the same provider looks stuck

Weighted-random across eligible providers; small samples look skewed. Run a simulation or ~10 card+ZAR purchases, or switch to performance routing.

Many payments stuck in pending no webhook

Confirmation webhooks haven't arrived. On the free tier, a large simulation burst can back up webhook delivery (single CPU) — use smaller runs, or wait for the backlog to drain. Otherwise it's a simulated undelivered outcome or a webhooksDisabled fault; reconciliation flags these as STATUS_MISMATCH.

First request is very slow ~30–60s

Free-tier cold start — the service sleeps after ~15 min idle. Hit /health first.

Deployment

Build fails: "Cannot find name 'process'" / missing @types build error

NODE_ENV=production makes npm skip devDependencies. Use npm install --include=dev (and for the web build), and/or NPM_CONFIG_PRODUCTION=false.

DB connect fails: ENETUNREACH … :5432 (IPv6) ENETUNREACH

Supabase's direct host is IPv6-only. Use the Session pooler string (aws-0-<region>.pooler.supabase.com:5432, IPv4).

DB: password authentication failed for user "postgres" 28P01

The pooler username must include the ref: postgres.<ref>, not bare postgres. Fix the username in DATABASE_URL.

DB: ECIRCUITBREAKER … temporarily blocked XX000

The pooler blocks after repeated auth failures. Fix credentials, then let it cool down (the app backs off; or suspend ~5 min).

Supabase won't connect after days idle paused

Free projects pause after ~7 days idle — restore it from the Supabase dashboard.
